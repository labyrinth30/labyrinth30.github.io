### 문제 · 조회 기간이 길수록 반복되는 검색 조건

관리자 주문 검색은 관련 사용자·상품·결제 조건을 상관 EXISTS 다섯 개로 확인했습니다. 조회 기간을 넓히면 각 주문마다 관련 테이블을 확인하는 반복 비용이 커졌습니다. 전체 기간 검색에서 대표 원번 조건의 기존 count SQL은 4.73초가 걸렸습니다.

### 내가 맡은 범위 · 공통 검색 필터와 실행 계획 개선

실행 계획을 분석하고, 관련 테이블에서 검색어와 일치하는 주문 ID를 먼저 모아 바깥 쿼리에 전달하도록 변경했습니다. 목록·건수·요약·엑셀이 공유하는 필터에 함께 적용하고, 다섯 검색 조건에서 변경 전후 결과 건수를 비교했습니다.

### 선택과 이유 · SQL을 나눠 반복 계산을 줄이기

하나의 SQL 안에 `IN(SELECT … UNION …)`을 넣는 대안도 확인했습니다. 그러나 MySQL이 이를 DEPENDENT SUBQUERY/UNION으로 실행해 반복 계산이 남았고, 해당 측정은 4.55초였습니다. ID 선별을 별도 SQL로 실행해 주문별 반복 평가를 분리했습니다.

SQL 왕복과 ID 전달 비용은 추가됩니다. 넓게 일치하는 검색은 이 비용이 커질 수 있어 모든 조건의 성능 개선을 주장하지 않습니다. 정렬이 병목이라는 근거가 없어 인덱스를 추가하지 않았으며, 일부 남은 EXISTS 비용도 유지했습니다.

### 측정 · 기존 count와 ID 조회+count 합계 비교

**2026년 9월 17일, MySQL 8.0.42, 주문 약 11.6만 행, 전체 기간**을 기준으로 측정했습니다. 아래 개선값은 **ID 조회와 count의 합계**이며 HTTP API 전체 응답 시간이 아닙니다. 단위는 초입니다.

| 검색 조건 | 기존 count | 개선 ID 조회+count | 기존·개선 결과 건수 |
| --- | ---: | ---: | ---: |
| 원번 | 4.73초 | 0.89초 | 171 = 171 |
| 무매칭 | 9.60초 | 0.56초 | 0 = 0 |
| 상품명 | 4.45초 | 1.16초 | 40,377 = 40,377 |
| 성씨 | 4.38초 | 0.88초 | 18,084 = 18,084 |
| 1글자 | 1.86초 | 1.95초 | 87,001 = 87,001 |

### 검증과 한계 · 빠른 조건과 느려진 조건을 함께 남기기

원번 조건은 4.73초에서 0.89초로 줄었지만, 1글자 조건은 1.86초에서 1.95초로 소폭 느려졌습니다. 다섯 조건의 **결과 건수 일치**를 확인한 범위이며 결과 행과 순서의 완전 동일성이나 반복 부하 성능을 증명한 수치는 아닙니다.

당시 관련 스펙 48건, 관리자 API 테스트 2,200건, 관련 패키지 빌드 14개 성공 기록을 확인했습니다. 기존 실패 및 미실행 통합 스펙이 있어 이를 전체 테스트가 모두 통과한 결과로 합치지 않았습니다. 이 표와 검증은 당시 기록이며, 이번 포트폴리오 작업에서 운영 DB나 원본 테스트를 재실행하지 않았습니다.
