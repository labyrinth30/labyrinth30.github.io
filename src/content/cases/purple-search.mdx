### 문제

관리자 주문 검색은 사용자·상품·결제 조건을 상관 EXISTS 다섯 개로 확인하고 있었습니다. 조회 기간이 길어질수록 주문마다 관련 테이블을 다시 보는 비용이 커졌고, 전체 기간에서 원번으로 검색하면 count SQL만 4.73초가 걸렸습니다.

### 맡은 일

실행 계획을 보고, 검색어에 맞는 주문 ID를 관련 테이블에서 먼저 뽑아 바깥 쿼리에 넘기도록 바꿨습니다. 목록, 건수, 요약, 엑셀이 같은 필터를 쓰기 때문에 한 번에 적용했고, 다섯 가지 검색 조건으로 변경 전후 결과 건수를 비교했습니다.

### 이렇게 한 이유

SQL 하나에 `IN(SELECT … UNION …)`을 넣는 방법도 해봤는데, MySQL이 DEPENDENT SUBQUERY/UNION으로 실행해서 반복 계산이 그대로였습니다(4.55초). 그래서 ID 뽑는 부분을 별도 SQL로 뺐습니다.

SQL 왕복과 ID 전달 비용이 생기기 때문에, 결과가 많이 걸리는 검색에서는 오히려 느려질 수 있습니다. 정렬이 병목이라는 근거는 없어서 인덱스는 추가하지 않았고, 남은 EXISTS 일부도 그대로 뒀습니다.

### 측정

**2026년 9월 17일, MySQL 8.0.42, 주문 약 11.6만 행, 전체 기간** 기준입니다. 개선 후 값은 ID 조회와 count를 합친 SQL 시간이고, API 전체 응답 시간은 아닙니다.

| 검색 조건 | 기존 count | 개선 ID 조회+count | 기존·개선 결과 건수 |
| --- | ---: | ---: | ---: |
| 원번 | 4.73초 | 0.89초 | 171 = 171 |
| 무매칭 | 9.60초 | 0.56초 | 0 = 0 |
| 상품명 | 4.45초 | 1.16초 | 40,377 = 40,377 |
| 성씨 | 4.38초 | 0.88초 | 18,084 = 18,084 |
| 1글자 | 1.86초 | 1.95초 | 87,001 = 87,001 |

### 검증과 한계

원번 검색은 4.73초에서 0.89초로 줄었지만 1글자 검색은 1.86초에서 1.95초로 조금 느려졌습니다. 다섯 조건 모두 결과 건수는 같았는데, 행 내용과 순서까지 같은지, 반복 부하에서 어떤지는 확인하지 않았습니다.

관련 스펙 48건, 관리자 API 테스트 2,200건, 관련 패키지 빌드 14개가 통과했습니다. 원래부터 실패하거나 실행되지 않는 통합 스펙이 있어서, 전체 테스트가 다 통과했다고 보긴 어렵습니다.
