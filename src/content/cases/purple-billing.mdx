### 문제 · 진입점이 달라도 청구 대상은 같은 구독

정기결제 배치, 관리자 수동 재결제, 학부모 셀프 재결제는 같은 구독을 청구할 수 있습니다. 관리자 API와 웹 API는 서로 다른 프로세스에서 실행되므로, 프로세스 내부의 보호 장치만으로는 동시 청구를 조율할 수 없습니다. 이름이 다른 락을 각각 잡는 방식도 서로의 진입을 막지 못합니다.

### 내가 맡은 범위 · 셀프 재결제를 기존 청구 흐름에 연결

실패 안내에서 기존 체크아웃으로 연결해 카드 선택과 셀프 재결제를 지원했습니다. 새 진입점을 추가하면서 배치·관리자 경로와 같은 Redis의 구독별 락을 공유하도록 통일하고, 기존 청구 처리를 재사용했습니다.

### 선택과 이유 · 락 안에서 최신 상태를 다시 확인

SETNX 기반 락을 획득한 뒤 구독, 최신 실패 결제, 처리 대기 결제를 다시 조회했습니다. 락을 기다리는 동안 다른 경로가 먼저 청구를 끝냈을 수 있기 때문입니다. 소유권, ACTIVE 상태, 최초 회차 제외, 처리 중 결제 유무, 재결제 기한을 검사한 뒤에만 청구를 진행했습니다. 관리자 수동 재결제는 CS 대응에 필요한 별도 기한 정책을 유지했습니다.

공유 락은 동시 진입을 조율하는 장치입니다. TTL은 180초이며, 외부 PG 호출과 DB 저장 전체를 하나의 원자적 작업으로 만들지는 못합니다. 청구 상태의 재검증과 외부 결제 결과 확인은 별도로 필요한 책임입니다.

### 검증과 한계 · 성공 청구까지 확인한 범위를 구분

당시 기록에서 재결제 가드와 알림 실패 처리 테스트를 확인했습니다. DEV 수동 QA는 재청구 요청, PG 실패 응답, 화면 안내까지 확인했지만 DEV 상점 설정 때문에 성공 청구는 미검증이었습니다. 이 범위를 성공 결제까지 검증한 결과로 확대하지 않습니다.

검증은 당시 개발 기록에 기반하며 이번 포트폴리오 작성 중 결제나 원본 서비스 테스트를 재실행하지 않았습니다. 회사 비공개 자료의 코드·로그·내부 링크 대신 담당 범위와 판단 기준을 요약했습니다.
