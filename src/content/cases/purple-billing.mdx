### 문제

정기결제 배치·관리자 수동 청구·학부모 재결제가 같은 구독을 동시에 청구할 수 있었습니다. 관리자 API와 웹 API는 별도 프로세스라서 청구 경로 간에 공통된 경합 제어가 필요했습니다.

### 내 기여와 해결

기존 팀의 공용 Redis 락을 **관리자·배치 청구에 구독 단위로 적용하고 TTL을 조정**했습니다. 학부모 재결제에도 동일한 키 규칙을 적용하고, 락 획득 뒤 구독과 결제 상태를 다시 조회하는 가드를 넣었습니다.

공용 락과 배치 전체 락은 기존 팀 구현을 활용했습니다. 이후 writer 재조회·회차 비교·카드 정보 부분 갱신은 팀의 보완이며, 청구 경로별 상태 검증 조건이 모두 같은 것은 아닙니다.

### 검증 결과

2026년 10월 5일 별도 Redis 7.2.7에서 실제 두 앱의 락 클래스와 청구 콜백 더블을 조합했습니다. **같은 구독에 30개 동시 요청×20회**, 매회 **콜백 1회·29개 거절**을 확인했습니다. 서로 다른 구독 3개의 콜백은 동시에 실행됐습니다.

예외 시 finally 해제와 토큰 소유자만 삭제하는 동작도 확인했습니다. 프로세스 강제 종료 후에는 축소한 TTL 2초가 만료되며 락이 풀렸습니다.

### 검증 범위

실제 HTTP 청구 경로·PG를 통합한 과금 시험은 아닙니다. 구독 경로는 락을 자동 연장하지 않으며, TTL 1초 시험에서 첫 처리 중 두 번째 진입이 재현됐습니다. 실제 운영 두 앱의 Redis 연결 대상 동일 여부와 이중 청구 감소율은 확인하지 않았습니다.
