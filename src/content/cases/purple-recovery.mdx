### 문제

PG에서 결제가 완료됐어도 응답이 유실되면 서비스는 결과를 알 수 없습니다. 이를 바로 실패로 처리하면 실패 안내나 재청구로 이어질 수 있어, 오류 응답과 실제 결제 상태를 구분해야 했습니다.

### 내 기여와 해결

카드·브랜드페이 승인과 자동결제에 **조회 기반 복구**를 적용했습니다. 상태 코드 없는 오류·5xx·이미 처리된 결제 오류에서 조회하고, **동일 주문번호·동일 금액·DONE**이 모두 맞을 때만 기존 성공 경로로 이어가게 했습니다.

이미 처리된 결제 오류는 4xx여도 조회하는 예외입니다. 그 외 명확한 4xx 거절은 조회하지 않으며, 404·미완료·불일치·조회 실패도 성공으로 복구하지 않습니다. 기본 PG 어댑터·결제 모델·성공 저장과 후속 처리는 기존 팀 구현을 활용했습니다.

### 검증 결과

2026년 10월 5일 실제 개발 브랜치의 관리자 주문·결제 메서드와 Redis를 사용하고, PG·DB는 더블로 대체했습니다. PG 더블이 완료 상태를 기록한 뒤 응답 유실 오류를 던지는 상황에서 **10개 동시 요청 중 1개 성공·9개 거절**을 확인했습니다.

청구 더블·복구 조회·결제 저장·성공 로그·회차 저장은 각각 **1회**, 회차는 **1→2**, 실패 안내는 **0회**였습니다. 오래된 회차 객체의 재시도는 추가 청구 없이 차단됐습니다.

### 검증 범위

결제 완료 저장 후 회차 저장 실패를 주입하자, 재실행이 새 결제번호로 청구 더블을 다시 호출했습니다. 최신 회차를 읽는 관리자 재요청도 다음 회차 청구로 진행할 수 있어 요청 단위 멱등성을 보장하지 않습니다. 실제 DB 트랜잭션·웹훅·쿠폰·학습권까지 포함한 exactly-once는 미검증입니다.

위 결과는 실제 PG 결제 성공이나 운영 복구 실적이 아닙니다. 과거 ‘최근 6일 카드 승인 41건 중 timeout 0건’은 도입 전 위험 조사였으며, 운영 복구 건수·이중 청구 감소율·사고 예방 건수는 미집계입니다.

### 기여와 수치의 범위

검색 SQL 사전 ID 선별·검색 연결, 구독 락 적용·키 규칙 통일·재조회 가드, 승인·자동결제 조회 복구가 본인 담당입니다. 공용 락·기본 결제 모델·성공 처리·주문 동률 정렬과 이후 writer·회차 가드 보완은 팀 구현입니다. AI 공동 작성 표기가 있는 작업을 무보조 단독 구현으로 소개하지 않습니다.

새 검증은 개발 브랜치 코드 기준으로 운영 배포를 확인한 자료가 아닙니다. 의존 빌드 후 **선택한 기존 테스트 11개 스위트·136건**이 통과했으며 전체 저장소 테스트 결과는 아닙니다. SQL 반복 측정·락·복구 조합 시험은 이 테스트 건수와 별도입니다.

수치는 특정 조건의 SQL 호출 시간과 격리 환경의 더블 실행 횟수에 한정합니다. API·화면 전체의 81% 개선, 모든 검색 결과 보존, 모든 장애의 이중 청구 차단이나 운영 복구 실적을 뜻하지 않습니다.
