### 문제

자동결제 호출에서 네트워크 오류나 타임아웃이 나도 PG 쪽에선 이미 결제가 끝났을 수 있습니다. 이걸 바로 실패로 기록하면 재결제 안내가 나가고, 같은 회차를 두 번 청구할 수 있습니다. 실제 사고가 난 건 아니고, 그럴 수 있는 경로를 막으려고 한 작업입니다.

### 맡은 일

자동결제 호출에서 결과가 불확실한 오류가 나면 주문번호로 PG에 상태를 조회하도록 했습니다. 배치·관리자 재결제와 웹의 첫 결제·셀프 재결제에 같은 기준을 적용했고, 복구 조건은 테스트와 결제 도메인 문서에 남겼습니다.

### 이렇게 한 이유

HTTP 상태 코드가 없는 오류, 5xx, 이미 처리된 결제라는 응답만 조회 대상으로 잡았습니다. 조회 결과가 **같은 주문, 같은 금액, DONE**일 때만 기존 성공 흐름으로 넘깁니다. 주문이 있다거나 결제가 진행 중이라는 것만으로는 성공 처리하지 않습니다.

약관 동의나 결제수단 조회 실패, 명확한 4xx 거절은 조회하지 않습니다. 결과가 정말 불확실한 경우만 조회해야 쓸데없는 호출도, 잘못된 성공 처리도 줄일 수 있다고 봤습니다.

### 실패 처리

404, 미완료, 주문·금액 불일치, 조회 실패는 원래 오류를 그대로 둡니다. 성공으로 복구한 건은 경고 로그를 남겨서 나중에 추적할 수 있게 했습니다. 조회 자체도 실패할 수 있으니 모든 경우가 자동으로 풀리는 건 아닙니다.

### 검증과 한계

타임아웃·5xx 복구, 각 실패 분기, 4xx일 때 조회하지 않는 경우를 테스트했습니다. 관리자 API 2,477건, 웹 API 546건, PG 관련 5건 테스트와 영향 패키지 13개 빌드가 통과했습니다.

이 변경으로 이중 청구가 실제로 몇 건 줄었는지는 측정하지 못했습니다.
