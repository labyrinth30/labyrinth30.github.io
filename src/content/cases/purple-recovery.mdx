### 문제 · 응답을 못 받았어도 결제는 끝났을 수 있음

자동결제 호출에서 네트워크 오류나 타임아웃이 발생해도, PG에서는 이미 청구를 완료했을 수 있습니다. 이를 즉시 결제 실패로 기록하면 재결제 안내가 나가 같은 회차를 다시 청구할 위험이 생깁니다. 이 작업은 확인된 피해를 복구한 사례가 아니라, 결제 상태가 어긋날 수 있는 경로를 줄이는 변경입니다.

### 내가 맡은 범위 · 불확실한 결과의 조회와 공통 판단 기준

자동결제 호출의 불확실한 오류에 주문번호 기반 PG 조회를 추가했습니다. 배치·관리자 재결제와 웹의 최초 결제·셀프 재결제에 같은 판단 기준을 적용하고, 복구 조건을 테스트와 결제 도메인 문서에 남겼습니다.

### 선택과 이유 · 성공 증거가 있는 결제만 복구

HTTP 상태가 없는 오류, 5xx, 이미 처리된 결제 응답을 상태 조회 대상으로 정했습니다. 조회 결과에서 **동일 주문·동일 금액·DONE**을 모두 확인한 경우에만 기존 성공 흐름으로 복구합니다. 단순히 주문이 존재하거나 결제가 진행 중이라는 이유로 성공 처리하지 않습니다.

약관 동의나 결제수단 조회의 실패, 명확한 4xx 거절은 복구 조회 대상에서 제외했습니다. 복구는 청구 요청의 결과가 불확실한 경우로 좁혀 불필요한 조회와 잘못된 성공 판정을 피했습니다.

### 실패 처리 · 확인할 수 없으면 원래 오류 유지

404, 미완료, 주문·금액 불일치, 상태 조회 실패는 원래 오류를 유지합니다. 성공으로 복구한 건은 경고 로그를 남겨 사후 추적할 수 있도록 했습니다. PG 조회가 추가되고 조회 자체도 실패할 수 있으므로, 모든 오류가 자동으로 해소된다고 보지는 않았습니다.

### 검증과 한계 · 분기 검증과 운영 성과를 구분

당시 기록에서 시간 초과·5xx 복구와 각 실패 분기, 명확한 4xx 미조회 테스트를 확인했습니다. 관리자 API 2,477건, 웹 API 546건, PG 관련 5건의 테스트 및 영향 패키지 13개 빌드 성공 기록이 있습니다. 이 숫자는 당시 개발 검증이며 이번 포트폴리오 작성 중 결제를 호출하거나 원본 테스트를 재실행한 결과는 아닙니다.

실제 이중 청구가 몇 건 줄었는지는 측정 기록이 없어 성과로 제시하지 않습니다. 공개 자료에는 비공개 원문 코드·로그·내부 식별자 대신 복구 판단과 검증 범위를 요약했습니다.
