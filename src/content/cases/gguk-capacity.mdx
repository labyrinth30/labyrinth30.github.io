### 문제

사용자 API와 내부 워커가 같은 Cloud Run의 처리 자리를 공유하는데 큐는 최대 5개를 동시에 보내고 있었습니다. KST 2026년 9월 12일 사용자 API `429`는 14건, 태스크 생성은 56건, 워커 dispatch 시도는 65건이었습니다. 기존의 ‘태스크 64건’은 UTC 기준 dispatch 시도 횟수였습니다. AI 타임아웃에 따른 워커 `503` 9건은 사용자 API `429`와 별도로 집계했습니다.

### 맡은 일

로그로 요청 거절과 워커 부하를 확인하고 큐의 `maxConcurrentDispatches`를 **5→1**로 낮췄습니다. 장소 추출의 스크래핑·이미지 업로드·AI 호출·지오코딩 시간을 나눠 기록하는 로그도 추가했습니다.

### 이렇게 한 이유

설정 변경 시점의 Cloud Run은 인스턴스 1개, 동시 요청 1개였습니다. 이 처리 용량에 dispatch를 맞춰 대기를 큐로 옮겼습니다. 링크 접수는 빠르게 응답할 수 있지만, 큐에서 오래 기다리면 사용자가 추출 결과를 보는 시점도 늦어집니다.

같은 서비스를 쓰는 이상 사용자 요청의 우선 처리는 보장되지 않습니다. 서버 증설이나 워커 분리는 부하와 비용을 보고 판단할 대안으로 남겼습니다.

### 운영 관측

적용 구간을 제외한 전후 각각 7일의 사용자 API 요청을 비교했습니다. 시각은 KST이며, 건수는 사용자 수가 아닌 요청 수입니다.

| 관측 구간 | 사용자 API 요청 | 429 | 발생률 |
| --- | ---: | ---: | ---: |
| 변경 전 · 9/10 13:40–9/17 13:40 | 5,892건 | 14건 | 0.2376% |
| 변경 후 · 9/17 13:45–9/24 13:45 | 1,643건 | 0건 | 0% |

**발생률은 0.2376%p 낮게 관측됐습니다.** 요청량·태스크 유입량·인스턴스 설정·다른 배포가 달라, 설정 변경만의 인과 효과로 단정하지 않았습니다. 같은 리비전 비교에서는 전후 모두 `429`가 0건이었습니다. 변경 후 관측을 **10/5 09:00까지** 확장하면 **1/2,181건**이었으며, 운영 API 지연 개선은 관측되지 않았습니다.

### 로컬 HTTP 근사 실험

운영 실측과 별도로 단일 처리 슬롯 모델에서 설정별 5회 반복했습니다. 사용자 `429`는 **1,023/2,250건→0/2,250건**, 태스크 최초 dispatch 대기 중앙값은 **2.48→37.20 모델 초**였습니다. 시간 축을 10배 압축한 근사 모델로, 운영 성능 수치가 아닙니다. 처리 자리 경합을 줄이는 대신 태스크 대기가 늘어나는 트레이드오프를 확인했습니다.

### 검증과 한계

PR #152는 인프라 코드의 Biome·TypeScript 검사, PR #153은 유닛 285건과 타입·정적 검사를 통과했습니다.

운영 관측은 설정 변경의 단독 효과를 입증하지 않습니다. 추가한 단계별 시간 로그도 DB 저장과 전체 실패 경로를 포함하지 않아, 작업 전체의 지연이나 유실 여부를 판단하는 지표로 쓰지 않았습니다.
