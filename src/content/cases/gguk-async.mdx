### 문제 · 링크 접수와 분석 완료는 다른 사건

GGUK는 Instagram 링크에서 장소를 추출해 방에 저장합니다. 스크래핑·AI 분석·지오코딩을 기다리는 동안 외부 서비스가 지연되거나, 여러 장소 중 일부만 처리될 수 있습니다. 접수 성공을 저장 완료처럼 취급하면 사용자에게 약속한 동작과 실제 데이터가 어긋납니다.

### 내가 맡은 범위 · 추출 결과를 저장까지 연결

팀이 구현한 AI 추출·지오코딩 로직을 바탕으로 접수 API와 내부 워커, DB 저장을 연결했습니다. 접수 단계에서 활성 방 멤버십과 URL을 검증하고, Cloud Tasks 등록이 성공한 뒤에만 `202 Accepted`를 반환합니다. 내부 워커에는 OIDC 인증을 적용했습니다.

### 선택과 이유 · 부분 성공을 버리지 않는 재시도

별도 job 테이블·jobId·폴링 API를 제거하고 접수와 처리를 분리했습니다. 중간 상태를 따로 동기화할 부담은 줄지만, 이 API의 응답은 접수 확인이며 최종 결과 알림은 아닙니다.

워커는 논리 장소별 지오코더 1순위 후보를 저장합니다. 성공한 장소·출처·핀을 먼저 커밋한 뒤, 일시적인 지오코딩 실패가 남아 있으면 `503`으로 재시도를 요청합니다. 이미 성공한 결과를 버리지 않으려면 같은 작업의 재배달도 안전해야 합니다. 장소는 upsert하고, 출처와 핀은 활성 행의 유니크 제약에 맞춰 충돌을 처리했습니다.

### 실제 코드 · 같은 방의 활성 핀 중복 방지

아래는 핀 INSERT에 이어지는 충돌 처리입니다. 방과 장소의 조합이 같고 삭제되지 않은 핀이 이미 있으면 추가 INSERT를 건너뜁니다. 삭제된 행은 활성 행 제약에서 제외되어 이후 재등록할 수 있습니다.

.onConflictDoNothing({

### 검증과 한계 · 접수 시간과 작업 시간을 구분

PR #74에는 실제 HTTP 요청과 embedded PostgreSQL로 접수→워커→저장, 부분 실패 후 재배달, 중복 배달, soft delete 이후 재유입을 검증한 기록이 있습니다. 당시 유닛 147건과 E2E 28건이 통과했습니다. 실제 GCP Cloud Tasks dispatch와 운영 OIDC 토큰 발급은 해당 로컬 검증에 포함되지 않았습니다.

운영 기록에서 **접수 응답은 0.2~0.7초**, **작업 시간 중앙값은 6.6초**였습니다. 작업 시간은 성공 73건 표본의 수치이며 p90은 13.2초입니다. 접수 응답과 작업 시간은 서로 다른 지표로, 분석 속도가 전후로 개선됐다는 비교가 아닙니다. 테스트와 측정값은 당시 PR 기록이며 이 포트폴리오 작성 중 원본 서비스를 재실행한 결과는 아닙니다.
