### 문제 · 트랜잭션 밖에서 들어오는 새 댓글

핀과 댓글을 한 트랜잭션으로 삭제해도, 댓글 삭제를 먼저 실행하면 그 뒤에 다른 요청이 새 댓글을 넣을 수 있습니다. 핀만 삭제되고 활성 댓글이 남는 경합입니다. 댓글 작성 전에 활성 핀을 조회하는 것만으로는 조회와 INSERT 사이의 삭제를 막지 못합니다.

### 내가 맡은 범위 · 삭제 API와 댓글 생성의 경합 제어

핀 삭제 API를 구현하면서 댓글 생성과 삭제가 지켜야 할 조건을 <strong>“삭제된 핀에는 활성 댓글이 남지 않는다”</strong>로 정했습니다. 삭제는 해당 방의 핀과 연결 댓글에만 적용합니다. 여러 방이 공유하는 장소 자체를 지우지 않아 다른 방의 저장 결과를 보존했습니다.

### 선택과 이유 · 두 작업이 같은 핀 행을 잠그도록

댓글 작성은 트랜잭션 안에서 활성 핀을 `SELECT … FOR SHARE`로 읽은 다음 댓글을 INSERT합니다. 핀 삭제는 먼저 핀을 UPDATE해 잠금을 확보하고, 같은 트랜잭션 안에서 연결 댓글을 soft delete합니다. 삭제 쿼리에는 활성 방 멤버 조건도 포함했습니다.

작성 트랜잭션이 먼저 잠금을 얻으면 삭제가 작성 커밋까지 기다립니다. 이후 댓글을 삭제하므로 방금 생성된 댓글도 삭제 범위에 들어갑니다. 반대로 삭제가 먼저 잠금을 얻으면 작성이 기다린 뒤 활성 핀이 없음을 확인하고 거절됩니다.

같은 핀의 작성과 삭제에는 잠금 대기가 생깁니다. 대신 댓글 작성끼리는 공유 잠금으로 병행할 수 있습니다. 애플리케이션의 사전 조회만으로 판단하지 않고, 상태 확인과 쓰기 사이를 DB 잠금으로 보호한 선택입니다.

### 실제 코드 · 트랜잭션 내부의 활성 핀 확인

```typescript
const [pin] = await tx
  .select({ id: pins.id })
  .from(pins)
  .where(and(eq(pins.id, pinId), isNull(pins.deletedAt)))
  .for("share");
```

### 검증과 한계 · 테스트 기록과 실행 순서 분석

PR #132에는 실제 HTTP 요청으로 핀·댓글 삭제, 목록 제외, 중복 삭제, 권한·입력 검증, 삭제 후 같은 장소 재등록을 확인한 기록이 있습니다. 당시 유닛 266건과 E2E 148건이 통과했습니다. 재등록은 활성 행만 대상으로 하는 partial unique 인덱스로 허용됩니다.

위 두 경합 순서의 설명은 머지된 코드의 공유 잠금과 핀 우선 UPDATE 순서를 대조한 결과입니다. 이를 두 실행 순서에 대한 별도 부하 테스트 실측으로 표현하지 않습니다. 테스트 건수는 당시 PR 기록이며 이번 포트폴리오 작업에서 원본 서비스를 재실행한 결과는 아닙니다.
